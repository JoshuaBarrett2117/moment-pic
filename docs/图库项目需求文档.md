# 图库项目需求文档

日期：2026-04-09
执行者：Codex

## 1. 项目目标

设计并实现一个本地图库项目，用于查看用户本地图片资源，并将不同来源的图片集合统一抽象为“图集”。

当前优先支持两类输入：

1. 文件夹图集：例如 `/图库/风景1/xxx.jpg`
2. ZIP 图集：例如 `/图库/风景2.zip`，ZIP 根目录下直接包含 `xx.jpg`

系统需要将上述两类资源统一识别为两个图集：

1. `风景1`
2. `风景2`

用户点击图集后，可以看到该图集下所有 JPG 图片的缩略图预览；点击某张图片后，进入大图浏览模式。

## 2. 产品定位

这是一个面向本地资源管理的桌面式图库应用，核心目标不是云同步，而是：

1. 快速扫描本地图库目录
2. 自动解构文件夹和 ZIP 为统一图集
3. 提供稳定、流畅的缩略图与大图浏览体验
4. 为后续扩展打下基础，例如收藏、标签、搜索、排序和增量更新

## 3. 核心概念

### 3.1 图库库位

用户配置一个或多个本地根目录，例如：

```text
/图库
```

系统从这些根目录下扫描可识别资源。

### 3.2 图集 Album

图集是统一抽象后的浏览单元。

支持两种来源：

1. 目录型图集：一个文件夹即一个图集
2. ZIP 型图集：一个 ZIP 文件即一个图集

图集需要具备以下基础元数据：

1. 图集唯一 ID
2. 图集名称
3. 来源类型：`folder` / `zip`
4. 原始路径
5. 图片数量
6. 封面图
7. 最近扫描时间
8. 更新时间

### 3.3 图片资源 Asset

图片是图集下的最小浏览单元。

图片需要具备以下基础元数据：

1. 图片唯一 ID
2. 所属图集 ID
3. 文件名
4. 文件扩展名
5. 排序序号
6. 原始访问地址
7. 缩略图地址
8. 宽高信息
9. 文件大小

## 4. 当前阶段功能范围

### 4.1 必须支持

1. 配置本地扫描根目录
2. 扫描文件夹图集
3. 扫描 ZIP 图集
4. 将两种图集统一展示在图库首页
5. 展示图集封面、名称、图片数量
6. 进入图集后展示图片缩略图网格
7. 点击缩略图进入大图查看模式
8. 大图模式支持上一张、下一张切换
9. 支持 JPG、JPEG、PNG、WEBP 的基础识别

### 4.2 当前阶段建议支持

1. 首次扫描建立索引
2. 二次启动读取索引，避免全量重复解析
3. 缩略图缓存
4. ZIP 图片按需读取，不一次性全部解压
5. 图集封面自动选首张图
6. 扫描失败或损坏文件提示

### 4.3 暂不纳入第一阶段

1. 用户登录
2. 云同步
3. 在线分享
4. 图片编辑
5. OCR
6. AI 分类
7. 视频支持

## 5. 关键业务流程

### 5.1 图集发现流程

1. 用户配置图库根目录
2. 后端扫描目录下的一级或多级资源
3. 识别文件夹型图集
4. 识别 ZIP 型图集
5. 提取图集名称
6. 建立图集记录和图片索引
7. 生成封面和缩略图缓存
8. 前端展示图集列表

### 5.2 图集浏览流程

1. 用户进入首页
2. 前端请求图集列表
3. 用户点击某个图集
4. 前端请求图集详情和图片列表
5. 后端返回缩略图访问地址
6. 前端以网格方式渲染所有预览图

### 5.3 单图查看流程

1. 用户点击缩略图
2. 前端打开大图查看器
3. 前端按需请求原图地址
4. 后端从本地文件或 ZIP 流中读取图片
5. 用户可切换上一张、下一张

## 6. 重点难点分析

### 6.1 统一抽象目录和 ZIP

这是项目最核心的架构点。

建议在后端定义统一的 `AlbumSource` 接口，对不同图集来源做同构处理：

1. 列举图片文件
2. 获取封面
3. 读取缩略图源
4. 读取原图流
5. 获取资源元数据

这样前端完全不需要关心图集来自目录还是 ZIP。

### 6.2 ZIP 的读取策略

ZIP 不建议在扫描阶段全部解压到磁盘。

建议策略：

1. 扫描阶段只读取 ZIP 条目列表和基础元数据
2. 生成缩略图时按需解压单张图片到内存
3. 原图查看时按需流式读取
4. 对常访问图片使用本地缓存

这样可以避免磁盘膨胀，也便于处理大 ZIP 文件。

### 6.3 缩略图缓存

图片预览数量一多，实时缩放会明显影响体验。

建议单独设计缩略图缓存层：

1. 以 `源文件路径 + 修改时间 + 条目标识` 生成缓存键
2. 将缩略图输出到本地缓存目录
3. 当源文件变化时自动失效重建

### 6.4 索引与增量更新

如果每次启动都全盘扫描，用户体验会变差。

建议：

1. 首次全量扫描
2. 后续基于文件修改时间做增量扫描
3. 用数据库保存图集与图片索引

## 7. 推荐架构

## 7.1 总体架构

根据补充约束，项目应采用 `Web 项目 + Docker 部署` 架构，而不是桌面应用。

推荐总体结构：

```text
Browser
    └─ Web Frontend（React / Next.js）

Docker Compose
    ├─ Gallery Web / API Service
    │   ├─ 图库扫描与索引模块
    │   ├─ 图集统一抽象层
    │   ├─ 缩略图生成模块
    │   ├─ 原图 / 预览图访问接口
    │   └─ 本地数据库
    └─ Volume Mount
        ├─ /data/library
        ├─ /data/cache
        └─ /data/db
```

也就是说，服务端容器通过挂载宿主机目录来访问图库资源，例如：

```text
宿主机：/图库
容器内：/data/library
```

系统从容器内挂载目录扫描资源，并对外提供图集、缩略图和原图访问接口。

这样做的原因是：

1. 符合 Web 项目和 Docker 部署形态
2. 可以集中处理文件扫描、ZIP 解析和缩略图缓存
3. 浏览器端无需直接访问本地文件系统
4. 便于后续部署到家庭服务器、NAS 或局域网环境

## 8. 技术栈建议

## 8.1 优先推荐方案

### 前端

1. `Next.js`
2. `React`
3. `TypeScript`
4. `TanStack Query`
5. `Tailwind CSS`
6. `shadcn/ui`

原因：

1. 适合 Web 项目，页面路由和数据获取组织更自然
2. 可以同时承载前端页面和部分 BFF 能力
3. 对 Docker 部署友好
4. 后续如果需要服务端渲染、SEO 或管理后台都比较自然

### 后端

优先建议两条路线二选一：

#### 方案 A：Node.js 统一栈

1. `NestJS` 或 `Fastify`
2. `TypeScript`
3. `SQLite`
4. `Prisma` 或 `Drizzle`
5. `sharp`
6. `yauzl` 或 `unzipper`
7. `fast-glob` 或 `fs/promises`

优点：

1. 前后端统一 TypeScript，开发效率高
2. `sharp` 在缩略图生成上成熟稳定
3. 更适合先快速做出第一版

缺点：

1. 大量图片处理和高并发场景下，长期性能上限不如 Rust 方案

#### 方案 B：前后端分离，后端走高性能路线

1. 前端：`Next.js + React + TypeScript`
2. 后端：`Rust + Axum`
3. `SQLite`
4. `sqlx`
5. `zip`
6. `image`
7. `walkdir`

优点：

1. 文件扫描、ZIP 读取、图片处理性能更强
2. 更适合长期演进成大图库服务

缺点：

1. 开发与协作复杂度更高
2. 前后端接口联调成本更高

## 8.2 当前更推荐的结论

基于你现在的目标描述，我更推荐第一阶段采用：

`Next.js + TypeScript + NestJS/Fastify + SQLite + sharp + yauzl + Docker Compose`

原因：

1. Web 形态下，这套技术栈更平衡开发效率与可维护性
2. 目录图集和 ZIP 图集的统一解构，用 Node.js 也完全能做好
3. 缩略图、分页、预览、缓存这些图库核心能力都能较快落地
4. 后续如果图片处理瓶颈明显，再把扫描和缩略图服务拆成独立 Rust 服务也不晚

## 8.3 我对技术路线的建议

如果你希望：

1. 更快上线和验证功能，选 `Next.js + NestJS/Fastify`
2. 一开始就为超大图库、极致性能做准备，选 `Next.js + Rust API`

就目前这个阶段，我建议优先走：

`Next.js + Fastify（或 NestJS）+ SQLite + sharp`

## 11. API 设计建议

建议采用标准 HTTP API，图片资源通过受控路由访问，而不是暴露宿主机原始路径。

建议接口保持统一：

1. `getLibraryRoots()`
2. `addLibraryRoot(path)`
3. `scanLibrary()`
4. `listAlbums()`
5. `getAlbumDetail(albumId)`
6. `listAssets(albumId, page, pageSize)`
7. `getAssetPreview(assetId)`
8. `getAssetOriginal(assetId)`

返回数据建议前后端统一 DTO，避免页面直接依赖底层文件结构。

## 15. Docker 部署建议

### 15.1 推荐部署结构

建议使用 `docker compose` 管理至少以下挂载：

1. 图库原始目录挂载到 `/data/library`
2. 缩略图缓存目录挂载到 `/data/cache`
3. SQLite 数据目录挂载到 `/data/db`

例如：

```yaml
services:
  app:
    build: .
    ports:
      - "3000:3000"
    volumes:
      - /宿主机/图库:/data/library:ro
      - /宿主机/图库缓存:/data/cache
      - /宿主机/图库数据库:/data/db
```

建议图库挂载采用只读：

1. 避免误修改原始图片
2. 服务只负责读取、索引和生成缓存

### 15.2 Web 部署下的关键注意点

1. 浏览器不能直接读取用户本地文件，必须由服务端扫描挂载目录
2. ZIP 原图访问建议走后端流式接口，不直接解压到公开静态目录
3. 缩略图可以缓存到磁盘后再通过静态或受控接口提供
4. 如果后续部署在 NAS，需要考虑路径配置和扫描权限

## 17. 当前建议结论

在 `Web + Docker` 前提下，这类需求最合适的方向是：

1. 用 Docker 挂载宿主机图库目录，由服务端统一访问本地文件
2. 用统一图集抽象屏蔽目录和 ZIP 差异
3. 用 SQLite 保存索引
4. 用缩略图缓存解决浏览性能问题
5. 以前后端分层方式为后续功能扩展留空间

推荐技术栈：

`Next.js + TypeScript + Fastify/NestJS + SQLite + sharp + Docker Compose`
