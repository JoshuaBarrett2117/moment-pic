# 大图页面画质选项可行性分析

日期：2026-04-20  
执行者：Codex

## 1. 需求结论

需求应收敛为：

1. 画质切换入口放在大图查看页内部。
2. 用户在看图过程中可以随时切换画质。
3. 设置页如果保留相关配置，建议只保存“默认画质”，不承担主要切换入口。

这个方向是合理的，也更符合当前产品使用方式。

## 2. 为什么建议放在大图页面内

把画质切换放在大图页面内，比只放设置页更合适，原因有三点：

1. 画质是强场景化操作。用户通常是在“当前这张图打开有点慢”或“当前这张图想看更清楚”时才想切换，不会专门先去设置页调整。
2. 切换收益需要立即反馈。用户在查看器里切换后，能马上看到清晰度和加载速度变化，这比去设置页修改再返回更自然。
3. 大图页已经有工具条。当前 [ViewerGallery.tsx](/C:/Users/a3875/Documents/code/moment-pic/apps/web/src/components/ViewerGallery.tsx) 内已有关闭、翻页、缩放、旋转、重置等操作，画质切换和这些操作属于同一层级。

结论：

大图页内切换应作为主入口，设置页最多做默认值兜底。

## 3. 当前实现现状

### 3.1 大图页现在直接读取原图

证据：

1. [api.ts](/C:/Users/a3875/Documents/code/moment-pic/apps/web/src/types/api.ts) 中资源项包含 `originalUrl`。
2. [ViewerGallery.tsx](/C:/Users/a3875/Documents/code/moment-pic/apps/web/src/components/ViewerGallery.tsx) 直接把 `item.originalUrl` 作为查看器图片源。
3. [assets.ts](/C:/Users/a3875/Documents/code/moment-pic/apps/server/src/routes/assets.ts) 中 `/api/v1/assets/:assetId/original` 会直接读取原始图片文件或压缩包条目。

这意味着：

1. 当前没有大图专用的预览图层。
2. 当前也没有用户可切换的画质档位。
3. 如果要支持页内画质切换，必须新增“大图预览图”能力，而不是继续只靠原图接口。

### 3.2 现有基础设施足够支撑

证据：

1. [thumbnail-service.ts](/C:/Users/a3875/Documents/code/moment-pic/apps/server/src/services/thumbnail-service.ts) 已经使用 Sharp 做图片缩放、转码和缓存。
2. 现有缩略图服务已经具备缓存键、并发限制、失败回退等能力。
3. [system-config.ts](/C:/Users/a3875/Documents/code/moment-pic/apps/server/src/routes/system-config.ts) 与 [sqlite-store.ts](/C:/Users/a3875/Documents/code/moment-pic/apps/server/src/services/sqlite-store.ts) 已有系统配置读写能力，可用于保存默认画质。

结论：

技术上可行，且不需要改扫描、索引、相册数据结构。

## 4. 推荐方案

推荐方案是“双层控制”：

1. 大图页面内提供即时切换入口。
2. 设置页仅保存默认画质。

实际优先级如下：

1. 页内切换是主功能。
2. 默认画质只是辅助体验，不是主交互。

## 5. 交互设计建议

### 5.1 入口位置

建议把画质切换放到查看器底部工具条中，与缩放、旋转、重置并列。

原因：

1. 当前底部工具条已经承载查看器操作，用户认知成本最低。
2. 工具条在移动端和桌面端都已有显示逻辑，复用最自然。
3. 切换时不需要离开当前图片。

不建议优先放的位置：

1. 设置页：太远。
2. 二级弹窗深层菜单：切换成本高。
3. 右键菜单：移动端不友好。

### 5.2 交互形式

建议使用以下两种形式之一：

1. 直接按钮循环切换：`均衡 -> 高清 -> 原图`。
2. 点击后展开轻量面板：显示 `省流 / 均衡 / 高清 / 原图`。

更推荐第二种，因为：

1. 状态更清楚。
2. 用户知道自己当前在哪一档。
3. 后续更容易扩展提示文案，例如“当前档位更慢”。

### 5.3 切换行为

建议切换行为如下：

1. 切换后立即重新请求当前图片。
2. 当前缩放、旋转、平移状态尽量保留，不要因为切画质而强制退出查看状态。
3. 切换过程中显示加载态。
4. 切换成功后，后续同一会话内的相邻图片预加载也使用当前档位。

其中第 2 点很重要。

因为用户切画质通常是为了“在当前观察上下文里继续看”，如果一切换就把缩放、位置全部重置，体验会比较割裂。

## 6. 技术实现建议

### 6.1 后端

建议新增大图预览接口，而不是改原图接口语义。

推荐接口：

1. `/api/v1/assets/:assetId/preview?preset=low|balanced|high`
2. `/api/v1/assets/:assetId/original`

规则建议：

1. `preview` 用于压缩预览图。
2. `original` 永远表示原图。
3. 当用户在页内选择“原图”时，前端直接切到 `/original`。

这样接口职责清晰，不会把“原图”变成伪原图。

### 6.2 前端

[ViewerGallery.tsx](/C:/Users/a3875/Documents/code/moment-pic/apps/web/src/components/ViewerGallery.tsx) 是主要改动点。

建议新增状态：

1. `qualityPreset`：当前查看器会话使用的画质档位。
2. `defaultQualityPreset`：从系统配置读取的默认档位。

建议图片源逻辑改为：

1. `balanced/high/low` 时使用 `preview` 地址。
2. `original` 时使用 `originalUrl`。

建议预加载逻辑也绑定当前档位，避免当前图和预加载图使用不同策略。

## 7. 档位建议

如果只做大图页，我建议首版控制在 3 个主档位加 1 个原图档位：

1. `low`：长边 1600，适合弱网或 NAS。
2. `balanced`：长边 2560，默认档位。
3. `high`：长边 3840，适合大屏细看。
4. `original`：原始图片。

建议文案：

1. 省流
2. 均衡
3. 高清
4. 原图

这个命名比 `low/high` 更像面向用户的产品语言。

## 8. 性能与体验影响

### 8.1 正向收益

如果页内支持随时切换，收益会比“只在设置页改默认值”更明显：

1. 用户遇到慢图时可以立刻降档。
2. 用户遇到细节图时可以立刻升档。
3. 查看器体验更可控，不需要退出当前浏览流程。

### 8.2 注意点

页内切换也会带来新的细节要求：

1. 切换后要避免读到旧缓存。
2. 切换时要避免闪烁太重或长时间白屏。
3. 高画质和原图档位下，预加载策略需要收敛。

建议：

1. `balanced` 保持现有预加载策略。
2. `high` 适当减少预加载数量。
3. `original` 默认只加载当前图，或者只预加载后一张。

## 9. 风险分析

### 9.1 切换后状态被重置

这是页内切换最容易出体验问题的点。

如果用户已经放大并拖到某个局部，再切画质时被强制重置，会感觉像“重新打开了一次图”。

建议：

1. 切换画质时尽量保留缩放和位置。
2. 只有在图片天然尺寸差异导致当前位移越界时，才做温和纠正。

### 9.2 原图档位过重

原图档位在超大图片、压缩包图片或网络磁盘场景下可能明显更慢。

建议：

1. 原图不要作为默认值。
2. 页内文案明确提示“最清晰，可能更慢”。

### 9.3 控件过多挤占工具条

当前查看器底部已经有四个按钮，如果再新增画质控制，移动端空间会更紧。

建议：

1. 画质入口做成一个独立按钮。
2. 点击后弹出轻量选择面板，不要把四个档位直接平铺在主工具条里。

## 10. 实施成本评估

如果按照“页内即时切换 + 设置页默认值”的方案，预计成本属于中等：

1. 后端预览接口与缓存变体支持：0.5 到 1 人日。
2. 查看器页内切换控件与状态管理：0.5 到 1 人日。
3. 默认值配置接入与联调：0.5 人日。

总计约 1.5 到 2.5 人日。

## 11. 建议的最小可落地版本

建议首版做以下内容：

1. 查看器底部工具条新增“画质”按钮。
2. 点击后弹出三档或四档选项。
3. 切换后立即刷新当前图片源。
4. 默认档位从系统配置读取。
5. 设置页只提供“默认大图画质”设置，不承担主要切换功能。

这是当前最平衡的实现方式。

## 12. 最终结论

“画质切换放在大图页面进行，方便用户随时切换”这个判断是正确的，且比“只放设置页”更适合当前项目。

推荐最终方案是：

1. 大图页面内提供即时画质切换。
2. 后端新增 `preview` 预览图接口。
3. 原图接口继续保留。
4. 设置页只保存默认画质。

这样既能满足随时切换的使用习惯，也能把实现复杂度控制在合理范围内。
