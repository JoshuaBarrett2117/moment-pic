# 架构评估与重构建议

日期：2026-05-03
执行者：Codex

## 1. 评估结论

当前项目已经具备基础的分层结构，但还没有形成稳定、可持续约束团队开发的架构原则。

整体判断如下：

- 优点：目录分层已经存在，后端具备 `routes -> services -> db/lib/types` 的基本组织方式。
- 优点：部分模块职责相对集中，例如扫描、缩略图生成、相册聚合逻辑已经按业务主题拆分。
- 优点：后端已有一定测试覆盖，说明核心模块具备基础可验证性。
- 问题：数据访问层过于集中，个别文件承担过多职责，模块边界开始模糊。
- 问题：前端顶层状态编排集中在 `App.tsx`，页面导航、认证、URL 状态同步、数据刷新耦合较深。
- 问题：数据库访问策略不统一，Prisma Schema 与手写 SQLite 引导逻辑并存，但没有统一主策略。

结论：当前代码结构有“比较合理的设计方向”，但还不能说“已经有一套清晰且稳定的设计原则在支撑整个项目”。

## 2. 当前代码结构判断

### 2.1 后端

后端结构主要集中在 `apps/server/src/`：

- `index.ts`：启动入口。
- `app.ts`：应用装配与中间逻辑注册。
- `routes/`：HTTP 接口层。
- `services/`：业务逻辑层。
- `db/`：数据库初始化。
- `lib/`：通用工具。
- `types/`：DTO 与存储层类型。

这说明后端已经在实践以下原则：

- 关注点分离
- 分层组织
- 面向业务模块拆分

但这些原则目前是“软约束”，不是“硬边界”。主要风险是：

- `sqlite-store.ts` 体量过大，已接近全局仓储中心。
- `routes` 中混入了部分资源调度与并发控制逻辑。
- 业务服务层与数据访问层之间缺少更明确的仓储边界。

### 2.2 前端

前端结构主要集中在 `apps/web/src/`：

- `components/`：页面和 UI 组件。
- `hooks/`：数据获取与交互封装。
- `lib/`：API 调用与工具逻辑。
- `types/`：前端 DTO 类型。

这说明前端已经有一定模块拆分意识，但仍存在以下典型问题：

- `App.tsx` 同时承担应用入口、导航状态、认证状态、URL 同步、页面切换和刷新协同。
- `hooks` 主要还是 API 请求封装，尚未形成稳定的页面状态模型。
- 页面容器组件与纯展示组件尚未完全分离。

结论是：前端当前更像“可以工作的集中式编排”，而不是清晰的应用分层。

## 3. 设计原则落地情况

### 3.1 已经部分落地的原则

#### 单一职责原则（SRP）

部分模块已经体现：

- `library-scanner.ts` 负责图库扫描。
- `thumbnail-service.ts` 负责缩略图与预览图生成。
- `album-service.ts` 负责相册聚合与 DTO 输出。

但也存在明显破坏：

- `sqlite-store.ts` 职责过多。
- `App.tsx` 职责过多。

#### 关注点分离（Separation of Concerns）

后端比前端做得更好。路由、服务、工具、类型基本分开，说明已有意识。

但关注点分离还没有彻底落实：

- 路由层仍包含一部分业务策略与并发控制。
- 前端页面顶层状态过于集中。

#### 模块化与可维护性

项目已经按业务特性拆出若干模块，例如：

- 相册
- 资源
- 扫描
- 自动整理
- 缩略图

这说明“按业务域拆分”方向是对的。

不足在于：

- 数据访问层未按业务域拆分。
- 前端状态层未按页面或领域拆分。

### 3.2 尚未稳定落地的原则

#### 依赖方向清晰

目前没有看到明确的架构规则去保证：

- route 只能依赖 service
- service 只能依赖 repository/lib
- 前端页面只能通过 hooks 或 controller 获取数据

因此依赖方向主要靠开发习惯维持，后续容易失控。

#### 一致性原则

数据库层目前存在两套并行思路：

- `prisma/schema.prisma`
- `better-sqlite3 + 手写建表/迁移逻辑`

如果不统一，后续会带来以下问题：

- 真实数据结构来源不明确
- 迁移策略难以维护
- 新功能开发时不知道应该扩展哪一层

## 4. 当前最主要的结构风险

### 风险 1：数据访问层过于集中

`apps/server/src/services/sqlite-store.ts`

问题：

- 文件过长
- 业务域混杂
- SQL、映射、事务、仓储方法全部堆叠

影响：

- 修改一个领域时容易影响另一个领域
- 难以定位问题
- 测试粒度会越来越粗

### 风险 2：前端顶层编排过重

`apps/web/src/App.tsx`

问题：

- 状态种类过多
- 页面流程与数据流程耦合
- 历史状态同步与视图切换杂糅

影响：

- 继续加功能时很容易出现状态回归
- 页面切换和筛选逻辑的修改风险高
- 测试难度增加

### 风险 3：数据库主策略不统一

问题：

- Prisma 存在，但运行时主要依赖手写 SQLite 逻辑
- 模型定义与真实引导逻辑可能逐渐偏离

影响：

- 架构认知成本高
- 新成员很难快速理解数据层规则

## 5. 推荐的重构方向

### 第一优先级：拆分后端仓储层

目标：把 `sqlite-store.ts` 按领域拆开。

建议拆分为：

- `repositories/library-root-repository.ts`
- `repositories/album-repository.ts`
- `repositories/asset-repository.ts`
- `repositories/system-config-repository.ts`
- `repositories/smart-album-repository.ts`

原则：

- 一个仓储文件只负责一个领域。
- 映射函数跟随领域放置。
- 事务逻辑仅保留在需要跨表原子操作的仓储中。

### 第二优先级：收紧路由层职责

目标：让 `routes` 只负责 HTTP 协议转换。

建议：

- 参数解析、响应码映射保留在 route。
- 并发控制、任务编排、资源配额等逻辑迁移到 service。
- route 不直接承载复杂状态机。

### 第三优先级：拆分前端顶层应用编排

目标：缩小 `App.tsx` 的职责范围。

建议拆成三层：

- `app-shell`：负责应用骨架与页面挂载。
- `navigation-state`：负责 URL、历史、页面切换状态。
- `gallery-controller`：负责图库页相关数据刷新与筛选协同。

理想结果：

- `App.tsx` 只做装配。
- 页面状态逻辑迁移到 hooks 或 controller。
- 展示组件专注渲染。

### 第四优先级：统一数据库策略

目标：明确“谁才是数据结构真相来源”。

可选方案：

- 方案 A：保留 `better-sqlite3` 为主，Prisma 仅删除或停用。
- 方案 B：逐步转向 Prisma，运行时数据访问统一走 Prisma。

当前从现状看，更现实的是：

- 短期内先以 `better-sqlite3` 为主。
- 将 Prisma 标记为待淘汰或待收敛。
- 避免双轨并行继续扩大。

## 6. 推荐目标结构

后端建议演进为：

```text
apps/server/src/
  app.ts
  index.ts
  routes/
  services/
  repositories/
  db/
  lib/
  types/
```

前端建议演进为：

```text
apps/web/src/
  app/
  pages/
  components/
  hooks/
  lib/
  types/
```

其中：

- `pages/` 放页面容器组件
- `components/` 放可复用展示组件
- `app/` 放应用装配、导航和全局状态协调逻辑

## 7. 最终判断

如果问题是：

“当前代码结构是否有比较合理的设计原则支撑？”

我的结论是：

- 有一定支撑，但不够稳。
- 后端比前端更接近合理分层。
- 当前更像“有架构意识”，还不是“有严格架构约束”。

如果下一步要继续演进，最值得优先做的不是重写功能，而是：

1. 先拆仓储层。
2. 再拆前端 `App.tsx`。
3. 最后统一数据库策略。

这样改动收益最高，也最能降低后续功能开发时的结构债务。
