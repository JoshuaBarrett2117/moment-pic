# 项目开发规范

日期：2026-04-18  
执行者：Codex

## 1. 文档目的

本文档基于项目中已经出现过的测试问题、回归问题和历史修复记录整理，目标不是罗列空泛的通用规则，而是把已经踩过的坑沉淀为可执行的开发规范，避免同类问题再次进入测试和回归阶段。

本文档主要参考以下已有证据：

- `apps/server/src/services/archive.test.ts`
- `apps/server/src/services/library-scanner.test.ts`
- `apps/server/scripts/browser-check.mjs`
- `docs/browser-regression-checklist.md`
- Git 历史中的归档支持、资产 ID 稳定性、归档刷新流程、移动端适配相关修复

## 2. 适用范围

- 后端扫描、归档读取、缩略图、资源接口开发
- 前端图库、相册详情、图片查看器、设置页等高频交互页面开发
- 涉及构建、工作区依赖、浏览器回归验证的交付场景

## 3. 核心开发规范

### 3.1 中文内容与编码规范

#### 坑 1：中文乱码问题反复出现，影响界面、文档和回归结果判断

历史表现：

- 项目已有浏览器回归清单明确要求检查“是否仍存在乱码文本”。
- `verification.md`、`docs/browser-regression-checklist.md` 等文件在终端中曾出现过乱码痕迹，说明编码问题不是单点问题，而是文档、前端文案、归档文件名都会受影响。

开发规范：

- 项目中的中文内容必须统一使用 UTF-8 编码保存，禁止混用 GBK、ANSI、UTF-8 with BOM 等不一致编码。
- 任何新增或修改的中文文案，都必须保证在编辑器、终端、浏览器中可正常显示，不能只在单一工具里看起来正常。
- 只要涉及中文文件名、中文路径、中文压缩包名、中文界面文案、中文日志输出，就必须显式评估编码链路，不得默认假设“运行环境会自动处理好”。
- 发现中文乱码时，必须直接修复源头编码或解码逻辑，禁止通过替换文案为英文、删除中文、绕过展示等方式规避问题。
- 文档、日志、接口返回、前端提示文案如果需要包含中文，提交前必须至少做一次实际显示检查。

验证要求：

- 浏览器回归时必须检查页面标题、按钮、提示文案、错误信息、空状态文案是否存在乱码。
- 涉及文档改动时，必须确认文档在仓库内重新打开后仍为正常中文。
- 涉及压缩包、路径、文件名展示时，必须补一次中文样本验证。

### 3.2 归档格式与文件名处理

#### 坑 2：只按 ZIP 思维实现，导致 RAR/CBR 场景失效

历史表现：

- 项目后续专门补入了 RAR/CBR 支持，并新增了真实归档测试。
- `archive.test.ts` 已明确覆盖 `rar -> cbr` 的识别与真实归档读取。

开发规范：

- 任何归档能力变更都必须同时考虑 `zip`、`cbz`、`rar`、`cbr`、`7z`，不能只验证单一格式。
- 新增归档能力时，必须同时覆盖“格式识别”和“真实内容读取”两类验证。
- 归档读取逻辑不得把扩展名别名当成不同协议分支重复实现，必须先统一归档类型，再进入读取流程。

验证要求：

- 至少验证 `detectArchiveType`、`isArchiveFile`、`listRootImageEntries`、`readArchiveEntryBuffer` 四条主链路。
- 测试优先使用真实样本，而不是只做字符串级 mock。

#### 坑 3：压缩包内文件名编码不一致，中文或特殊字符出现乱码

历史表现：

- 当前 `archive.ts` 已针对 ZIP 和 7z 在 Windows 环境下增加编码分支处理。
- `docs/browser-regression-checklist.md` 已把乱码文本列入重点观察项。

开发规范：

- 处理压缩包条目名称时，必须显式区分 UTF-8 标记、系统平台和 Windows 编码兼容场景。
- 凡是涉及文件名展示、归档条目路径比对、封面图定位的逻辑，必须先做标准化路径与编码解码，禁止直接信任原始字节串。
- 新增文件来源时，如果可能包含中文目录名或压缩包内嵌目录，必须补一组包含中文路径的回归样本。

验证要求：

- 本地至少验证一次中文路径、中文压缩包名、压缩包内中文条目名。
- 浏览器回归时，必须检查界面是否出现乱码标题、乱码按钮或乱码提示文案。

### 3.3 资源标识与扫描一致性

#### 坑 4：资产 ID 不稳定，导致缩略图、详情页和缓存引用漂移

历史表现：

- Git 历史存在 `fix(server): stabilize asset ids and errors` 修复。
- `library-scanner.test.ts` 已补充“相同资源生成相同 ID”“归档条目变化后 ID 必须变化”的测试。

开发规范：

- 资产 ID 必须由稳定来源字段生成，至少包含 `sourceType`、`sourcePath`、`zipEntryPath` 这类可复现输入。
- 禁止在扫描阶段为资源使用随机 ID、时间戳 ID 或依赖遍历顺序的临时 ID。
- 任何会影响资源唯一性的字段调整，都必须同步评估缩略图缓存、详情接口、封面图引用是否受影响。

验证要求：

- 新增或修改扫描逻辑时，必须补充“相同输入稳定输出”“关键字段变化导致输出变化”的单元测试。
- 涉及缓存命中逻辑时，必须验证同一资源二次扫描后引用仍然有效。

#### 坑 5：归档刷新与扫描状态同步不完整，前后端状态不一致

历史表现：

- Git 历史存在 `Fix archive refresh flow` 修复，影响了前端扫描状态与归档读取流程。
- `useLibraryScan.ts` 维护了扫描状态、轮询、清理和完成回调，说明这个链路容易出现状态残留。

开发规范：

- 所有异步扫描流程必须定义完整状态机，至少覆盖 `pending`、`running`、`completed`、`failed` 和清理阶段。
- 轮询类逻辑必须有明确的停止条件、异常清理和组件卸载回收，禁止残留定时器或过期任务状态。
- 只要扫描结果会驱动页面刷新，就必须保证“任务状态结束”和“数据重新拉取”在同一流程中闭环完成。

验证要求：

- 至少验证成功扫描、失败扫描、重复触发扫描、页面卸载时轮询清理四种路径。
- 回归时必须检查设置页发起扫描后，图库页、相册页、查看器页是否都能看到最新数据。

### 3.4 缩略图、原图与错误回退

#### 坑 6：缩略图生成失败时直接报错，页面没有可用降级路径

历史表现：

- `assets.ts` 中已经存在“缩略图失败后回退原图”的处理分支。
- 同一处还补了缩略图排队、超时、忙碌状态头部信息，说明这里出现过高并发或失败体验问题。

开发规范：

- 所有媒体派生资源都必须设计回退路径，至少保证“缩略图失败时仍能读取原图”。
- 资源接口必须区分“资源不存在”“源文件缺失”“服务繁忙”这三类错误，禁止统一返回模糊错误。
- 高并发媒体处理必须有限流和排队上限，不能把压力直接传递到磁盘和图像处理库。

验证要求：

- 至少验证缩略图成功、缩略图失败回退原图、资源不存在、源文件丢失、服务繁忙五类结果。
- 回归时检查前端是否把不同错误状态展示为可理解的提示，而不是统一的失败 toast。

### 3.5 前端布局与交互回归

#### 坑 7：移动端 fixed 布局遮挡内容，导致按钮不可点、底部内容被压住

历史表现：

- 最近多次修复集中在移动端宽屏布局、查看器、侧边栏、图库和详情页。
- `docs/browser-regression-checklist.md` 明确把固定栏遮挡、底部安全区遮挡、按钮可点击区域不足列为重点检查项。

开发规范：

- 新增 `fixed`、`sticky`、抽屉、底部栏、浮层时，必须同步评估桌面端、平板端、手机端三个视口。
- 移动端底部导航、顶部控制栏、弹层按钮必须预留安全区，不得用桌面端间距直接复用。
- 高 `z-index` 组件上线前必须验证与 toast、抽屉、查看器、确认弹层之间的叠放关系。

验证要求：

- 浏览器回归至少覆盖 `1440px`、`768px`、`390px` 三档宽度。
- 必须实际点按删除、关闭、翻页、筛选、返回等高频按钮，不能只看静态截图。

#### 坑 8：查看器交互修改后，提示、进度、预加载或退出行为容易回归

历史表现：

- 查看器相关提交曾单独修复文件恢复与预加载。
- `browser-check.mjs` 已对查看器进度显隐、翻页、旋转、退出全屏等行为做自动化检查。

开发规范：

- 查看器相关改动必须同时检查“进入”“切图”“旋转/缩放”“退出”四类状态切换。
- 任何预加载优化都不能破坏当前图显示、进度提示显隐和键盘操作。
- 涉及全屏、键盘事件、手势交互的代码，必须确认异常退出后状态能正确复位。

验证要求：

- 自动化验证至少保留一次打开查看器、切换下一张、旋转、退出的完整流程。
- 人工回归时额外检查移动端控制条自动隐藏与再次唤起是否正常。

### 3.6 构建与工作区依赖

#### 坑 9：构建脚本或 workspace 依赖不完整，导致“代码没错但本地验不过”

历史表现：

- `verification.md` 与 `.codex/testing.md` 中出现过 web workspace 缺依赖、`vite` 不可解析、后续又恢复通过的记录。
- Git 历史也存在 Docker 与 workspace 安装路径修复。

开发规范：

- 修改前端或构建配置后，必须分别验证 workspace 级别的 `lint` / `build`，不能只验证根目录命令。
- 涉及 Docker、产物路径、工作区安装目录的变更，必须同步检查容器构建与本地构建是否一致。
- 新增依赖时必须确认其落在正确 workspace，而不是误装到根目录或遗漏到 lockfile 之外。

验证要求：

- 前端改动后至少执行 `npm run lint --workspace @moment-pic/web`。
- 后端改动后至少执行 `npm run build --workspace @moment-pic/server`。
- 涉及前端打包、静态资源或 Docker 时，必须补执行 `npm run build --workspace @moment-pic/web` 或对应容器构建验证。

### 3.7 图片查看器切图顺序

#### 坑 10：切换图片时先等图片加载完成，导致页面看起来“卡在上一张”

历史表现：
- 查看器切到下一张时，当前页码或序号虽然已经变了，但图片画面会继续停留在上一张，直到新图加载完成才切换。
- 这种实现会让用户误以为切图没有响应，尤其在大图、慢网速或首次打开图片时更明显。

开发规范：
- 图片查看器切图必须遵循“先切页、后加载”的顺序，禁止把页面切换动作绑定到图片 `onLoad` 之后。
- 切换到新图片时，必须立刻更新当前索引、页码或序号，并同步进入加载态或空态。
- 不得沿用上一张图片的可见画面作为新图片的过渡画面，避免让用户误判为未切换成功。
- 如需过渡效果，只能在新页已生效的前提下叠加加载提示、占位层或淡入动画。

验证要求：
- 切图后立即检查页码、序号或标题是否已变化。
- 加载较慢时，必须能看到新页对应的加载态，而不是旧图继续占位。
- 自动化验收脚本应覆盖“打开查看器 -> 切到下一张 -> 立即看到新页状态 -> 图片加载完成”这一完整链路。

## 4. 落地执行清单

每次提交前，至少完成以下自检：

1. 我这次改动是否触碰了中文文案、中文路径、归档读取、扫描、缩略图、查看器、移动端布局、构建配置中的任一高风险区域。
2. 如果触碰了高风险区域，是否补了对应单元测试或浏览器回归验证。
3. 如果修改了资源唯一性、缓存键或扫描结果，是否验证了旧数据不会失联。
4. 如果增加了浮层、固定定位或安全区相关 UI，是否验证了 `390px` 宽度下的真实点击路径。
5. 如果改动涉及工作区依赖或构建路径，是否分别在对应 workspace 执行了验证命令。
6. 如果本次改动包含中文内容，是否确认编辑器、终端、浏览器中的显示都正常，没有出现乱码。

## 5. 推荐验证基线

建议把以下内容作为默认验证组合：

- 后端单元测试：归档识别、归档读取、稳定资产 ID。
- 前端类型检查：`npm run lint --workspace @moment-pic/web`
- 后端构建检查：`npm run build --workspace @moment-pic/server`
- 前端构建检查：`npm run build --workspace @moment-pic/web`
- 浏览器回归：执行 `apps/server/scripts/browser-check.mjs` 或按 `docs/browser-regression-checklist.md` 逐项检查。
- 中文专项检查：检查页面文案、错误提示、设置项、文档内容、中文路径展示是否正常。

## 6. 结论

这份规范的核心原则只有一句话：凡是已经在测试、回归或历史修复里出过问题的地方，都不能再靠“这次应该没事”来放行，必须绑定明确的开发约束和验证动作。
